Homework 1 - A toy hash on secp256k1

Practical: build a toy example of hashing with elliptic curves (secp256k1) and study the statistical properties that a hash needs for cryptography.

1. The curve

secp256k1 is the curve used by Bitcoin and Ethereum for signatures. It is the set of points (x, y) with coordinates in the field Fp that satisfy

y² = x³ + 7   (mod p)

p = 2^256 - 2^32 - 977
n = FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFE BAAEDCE6 AF48A03B BFD25E8C D0364141   (prime order of the group)
G = (79BE667E F9DCBBAC 55A06295 CE870B07 029BFCDB 2DCE28D9 59F2815B 16F81798,
     483ADA77 26A3C465 5DA4FBFC 0E1108A8 FD17B448 A6855419 9C47D08F FB10D4B8)

Points can be added with the chord-and-tangent rule, and this makes them a group. Multiplying a point by an integer k (k·G) is fast, but going back from k·G to k is the discrete logarithm problem, believed to cost about 2128 operations on this curve. I wrote this arithmetic from scratch in js/ecc.js with JavaScript BigInt, without any library.

The main part is the addition of two points (js/ecc.js):

function add(a, b) {
  if (a === null) return b;
  if (b === null) return a;
  let lambda;
  if (a.x === b.x) {
    if (mod(a.y + b.y) === 0n) return null; // a = -b
    lambda = mod(3n * a.x * a.x * inv(2n * a.y));
  } else {
    lambda = mod((b.y - a.y) * inv(b.x - a.x));
  }
  const x = mod(lambda * lambda - a.x - b.x);
  return { x, y: mod(lambda * (a.x - x) - a.y) };
}

lambda is the slope of the line through the two points (or of the tangent, when they are the same point). The sum is the mirror image of the third point where that line meets the curve. Divisions are done mod p with the modular inverse (inv, extended Euclid). null is the point at infinity, which works as zero.

2. The construction

My toy hash maps a message to a point of the curve. The method is called "try and increment":

H(m):
  for ctr = 0, 1, 2, ...
      h = SHA-256( 0x01 || ctr || m )
      x = h mod p
      if x³ + 7 is a square mod p:        (this happens for about half of the x)
          y = sqrt(x³ + 7)                (p = 3 mod 4, so y = (x³+7)^((p+1)/4) mod p)
          choose the sign of y from a bit of SHA-256(0x02 || h)
          return (x, y)

This is the real code (js/ecc.js):

function hashToPoint(msg) {
  for (let ctr = 0; ; ctr++) {
    const pre = new Uint8Array(5 + msg.length);
    pre[0] = 1;
    new DataView(pre.buffer).setUint32(1, ctr);
    pre.set(msg, 5);
    const h = sha256(pre);
    const x = bytesToBig(h) % P;
    const rhs = mod(x * x * x + B);
    const y0 = powmod(rhs, SQRT_EXP);
    if (mod(y0 * y0) !== rhs) continue;
    const signBit = sha256(Uint8Array.from([2, ...h]))[0] & 1;
    const y = (y0 & 1n) === BigInt(signBit) ? y0 : P - y0;
    return { point: { x, y }, counter: ctr };
  }
}

The loop increases ctr until x³ + 7 has a square root. The root is found with one modular exponentiation (powmod); if squaring it does not give back x³ + 7, this x has no point on the curve and the next ctr is tried. The sign of y comes from a second SHA-256, so that it does not depend on x.

The digest is the compressed point (33 bytes: 02/03 + x). For the statistics below, the digest is its 256-bit x-coordinate.

Since the output is a point of a group, hashes can be added: the hash of a set is the sum of the hashes of its elements, H({a,b}) = H(a) + H(b). This idea is called ECMH (elliptic curve multiset hash, Maitin-Shepard, Tibouchi and Aranha, 2016). It lets you update the hash with one point addition when an element is added or removed, which a normal hash like SHA-256 cannot do.

5. Statistical properties

A good hash should behave like a random function. I run four tests, and each one compares what I observe with what a perfectly random 256-bit output would give.

  • Avalanche. Flipping one input bit should flip each output bit with probability 1/2. The number of flipped bits is then Binomial(256, 1/2): mean 128, standard deviation 8.
  • Bit balance. Each output bit should be 1 half of the time. For each of the 256 positions the count of ones is standardised into a z-score; with 256 positions we expect about 0.7 of them beyond |z| = 3.
  • Byte uniformity. The 256 byte values should be equally frequent: chi-square test with 255 degrees of freedom (p-value from the Wilson-Hilferty approximation).
  • Collisions. Truncating the output to k bits, the number of colliding pairs among N outputs should be close to N(N-1)/2 · 2-k (birthday paradox).

As a control I run the same tests on a deliberately bad hash (a polynomial hash Σ bi·257i mod 2256). If the tests are meaningful, my hash should pass and the control should fail.

These are the two main computations (js/stats.js). For the avalanche test I hash a random message, flip one random bit of it and count how many output bits change (the Hamming distance):

const m = randomBytes(L);
const h = hashFn(m);

const m2 = Uint8Array.from(m);
const bit = Math.floor(Math.random() * L * 8);
m2[bit >> 3] ^= 1 << (bit & 7);
const d = hamming(h, hashFn(m2));
hist[d]++; sum += d; sumSq += d * d;

For byte uniformity I compare the count of each byte value with the expected count and turn the chi-square statistic into a p-value:

const expectedBytes = (N * 32) / 256;
const chi = byteCount.reduce((a, c) => a + (c - expectedBytes) ** 2 / expectedBytes, 0);
const pChi = chi2PValue(chi, 255);

6. Discussion

With the default settings my toy hash passes all four tests and the control fails all of them: its output is biased (for short messages the high bits are always 0), so the bit-balance and chi-square tests reject it and it collides far too often. So the tests are able to detect a bad function.

The tests are random too. A good hash can sometimes give one borderline result (for example a chi-square p-value of 0.02): in that case I re-run with a larger N instead of concluding that the hash is broken.

Why does it pass? The x-coordinate is basically the output of SHA-256 (apart from a negligible reduction mod p), so the good statistics come from SHA-256, not from the curve. What the curve adds is the group structure, i.e. the property H(a)+H(b) above, and a security argument based on discrete-log-type problems for the multiset version. Passing statistical tests is necessary but not sufficient: they cannot prove collision or preimage resistance, they only fail to find defects.

Limits: the toy hash is slower than SHA-256 (a square root mod p for each attempt, about two attempts on average), the number of attempts is not fixed, so it is not constant time, and the code is written to be clear, not to be used for real.
