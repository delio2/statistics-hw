Homework 1 - A toy hash on secp256k1

Practical: build a toy example of hashing with elliptic curves (secp256k1) and study the statistical properties that a hash needs for cryptography.

1. The curve

secp256k1 is the curve used by Bitcoin and Ethereum for signatures. It is the set of points (x, y) with coordinates in the field Fp that satisfy

y² = x³ + 7   (mod p)

p = 2^256 - 2^32 - 977
n = FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFE BAAEDCE6 AF48A03B BFD25E8C D0364141   (prime order of the group)
G = (79BE667E F9DCBBAC 55A06295 CE870B07 029BFCDB 2DCE28D9 59F2815B 16F81798,
     483ADA77 26A3C465 5DA4FBFC 0E1108A8 FD17B448 A6855419 9C47D08F FB10D4B8)

Points can be added with the chord-and-tangent rule, and this makes them a group. Multiplying a point by an integer k (k·G) is fast, but going back from k·G to k is the discrete logarithm problem, believed to cost about 2128 operations on this curve. The code in js/ecc.js implements this arithmetic with JavaScript BigInt.

2. The construction

The toy hash maps a message to a point of the curve ("try and increment"):

H(m):
  for ctr = 0, 1, 2, ...
      h = SHA-256( 0x01 || ctr || m )
      x = h mod p
      if x³ + 7 is a square mod p:        (this happens for about half of the x)
          y = sqrt(x³ + 7)                (p = 3 mod 4, so y = (x³+7)^((p+1)/4) mod p)
          choose the sign of y from a bit of SHA-256(0x02 || h)
          return (x, y)

The digest is the compressed point (33 bytes: 02/03 + x). For the statistics below, the digest is its 256-bit x-coordinate.

Because the output lives in a group, hashes can be added. The hash of a multiset is the sum of the hashes of its elements, H({a,b}) = H(a) + H(b). This is the idea behind ECMH (elliptic curve multiset hash, Maitin-Shepard, Tibouchi and Aranha, 2016), which gives an incremental hash: adding or removing one element costs one point addition instead of rehashing everything. Ordinary hashes such as SHA-256 cannot do this.

5. Statistical properties

A good hash should behave like a random function. Four properties are tested. Each one compares what is observed with the value expected from a perfectly random 256-bit output.

  • Avalanche. Flipping one input bit should flip each output bit with probability 1/2. The number of flipped bits is then Binomial(256, 1/2): mean 128, standard deviation 8.
  • Bit balance. Each output bit should be 1 half of the time. For each of the 256 positions the count of ones is standardised into a z-score; with 256 positions we expect about 0.7 of them beyond |z| = 3.
  • Byte uniformity. The 256 byte values should be equally frequent: chi-square test with 255 degrees of freedom (p-value from the Wilson-Hilferty approximation).
  • Collisions. Truncating the output to k bits, the number of colliding pairs among N outputs should be close to N(N-1)/2 · 2-k (birthday paradox).

As a control, the same tests are run on a deliberately bad hash (a polynomial hash Σ bi·257i mod 2256). If the tests are meaningful, the toy hash should pass and the control should fail.

6. Discussion

The toy hash passes all four tests, and the control fails them in an obvious way: its output is biased (the high bits never change for short messages), so the bit-balance and chi-square tests reject it immediately and it collides far too often. This shows the tests have enough power to detect a bad function.

It is important to be honest about why the toy hash passes. The x-coordinate is, up to a negligible reduction mod p, the output of SHA-256, so its statistical quality is inherited from SHA-256. The elliptic curve does not improve it. What the curve adds is a group structure: the algebraic property H(a)+H(b) above, and a security argument that reduces to the hardness of discrete-log-type problems for the multiset version. Passing statistical tests is necessary but not sufficient: they cannot prove collision or preimage resistance, they only fail to find defects.

Practical limits of this toy: it is slower than SHA-256 (a square root modulo p per attempt, about two attempts on average), the number of attempts is variable (so it is not constant time), and the code is written for clarity, not for real use.
