Homework 2 - Caesar cipher and a toy ECC scheme: encryption and attacks

The same message encrypted with both schemes, a comparison, and a statistical attack and a key-space attack.

I encrypt the same message with the Caesar cipher and with a toy scheme based on elliptic curves, compare the two, break the Caesar cipher with letter statistics, and break the toy ECC scheme by exploiting its small private-key range.

1. The message and the two schemes

The toy ECC scheme

In Homework 1 a public key Q = dG was computed with scalar multiplication. A public key can also be used to encrypt, by combining it with a fresh secret key (this is the idea of ECIES, an elliptic-curve version of ElGamal encryption). As the exercise says, I use secp256k1 with the private key restricted to a small range (1 to 216), so that the attack of section 4 can run in the browser. (In Homework 1, exercise 1, the toy curve with p = 17 was suggested; it is too small to carry a message.)

  1. Key generation. Choose a private key d in the small range and compute the public key Q = dG. Q is published and d is kept secret.
  2. Encryption (by anyone who knows Q). Choose a fresh random secret r (256 bits), compute R = rG and the shared point S = rQ. The keystream is the 32 bytes of the x-coordinate of S, and the ciphertext is c = message XOR keystream. The pair (R, c) is sent.
  3. Decryption (by the owner of d). Compute S = dR = d(rG) = r(dG) = rQ, derive the same keystream and compute message = c XOR keystream.

Role of the keys: d is needed to decrypt, Q lets anyone encrypt, r is a one-time secret that makes every encryption different, R lets the receiver rebuild S without ever knowing r, and S is the secret that sender and receiver can both compute. The code (js/toyecc.js):

// key generation: the private key d is restricted to 1 .. 2^16 (a small range, so that the attack can run in the browser)
const KEY_BITS = 16;
function keyPair() {
  const d = 1n + randomBelow(1n << BigInt(KEY_BITS));
  return { d, Q: C.mul(d) };
}

// encryption with the public key Q (message: at most 32 bytes): r is a fresh secret, R = rG is sent along
function encrypt(message, Q) {
  const r = 1n + randomBelow(C.n - 1n);
  const R = C.mul(r);
  const S = C.mul(r, Q);                                  // shared point S = rQ
  return { R, c: xor(message, keystream(S)), r };
}

// decryption with the private key d: dR = d(rG) = r(dG) = rQ = S, so the keystream is the same
function decrypt({ R, c }, d) {
  const S = C.mul(d, R);
  return xor(c, keystream(S));
}

The Caesar cipher

The Caesar cipher moves every letter k places in the alphabet (k = 0, ..., 25) and decryption moves it back. The same key k is used for both (js/caesar.js):

// Caesar cipher: every letter is moved k places in the alphabet; other characters are kept
const shift = (text, k) => text.toUpperCase().replace(/[A-Z]/g, (c) => String.fromCharCode((((c.charCodeAt(0) - A + k) % 26) + 26) % 26 + A));
const encrypt = (text, k) => shift(text, k);
const decrypt = (text, k) => shift(text, -k);

2. Similarities and differences

They have in common that a secret is needed to decrypt, that decryption is the exact inverse of encryption, and that the message is masked symbol by symbol (shifted letters, or bytes XORed with a keystream).

Caesar cipherToy ECC scheme
EncryptionAdd the key k to every letter (mod 26). The same key k is used to decrypt (symmetric cipher).With the public key Q: choose a fresh random r, send R = rG and c = message XOR the bytes of x(S), where S = rQ (public-key scheme).
DecryptionSubtract k from every letter.With the private key d: S = dR (= rQ), then message = c XOR the bytes of x(S).
Key space26 keys (25 useful).Here 216 = 65,536 private keys. An unrestricted secp256k1 key has about 2256 ≈ 1.2 · 1077 values.
Statistical propertiesEvery letter is always replaced by the same letter, so the letter frequencies of the language are kept (only moved by k places) and reveal the key.Each byte is XORed with a byte of x(S), which is different for every fresh r and looks random: the ciphertext bytes look uniformly random whatever the message is, so there are no letter statistics to exploit.

3. Statistical cryptanalysis of the Caesar cipher

The attack uses a corpus, a text of a known language. Mine has about 3,500 letters (js/corpus.js, written for this homework; a real attack would use a much larger corpus). The relative frequency of each letter in the corpus is the model of the language. The algorithm:

  1. Measure the model: the frequency of each letter in the corpus.
  2. For each of the 26 keys, decrypt the ciphertext and measure how far its letter counts are from the model with the chi-square distance χ² = Σ (observed - expected)² / expected, where expected = (number of letters) · (model frequency).
  3. The key with the smallest χ² is the guess.
// chi-square distance between the letter counts of a text and the model: small = looks like the language
function chiSquare(text) {
  const obs = counts(text), n = obs.reduce((a, b) => a + b, 0);
  return obs.reduce((sum, o, i) => sum + (o - n * MODEL[i]) ** 2 / (n * MODEL[i]), 0);
}

// key recovery: try the 26 shifts and keep the one whose decryption looks most like the language
function crack(cipher, score = chiSquare) {
  const table = [];
  for (let k = 0; k < 26; k++) table.push({ key: k, score: score(decrypt(cipher, k)) });
  const best = table.reduce((b, row) => (row.score < b.score ? row : b));
  return { key: best.key, table };
}

The test below uses text that is not in the corpus (the second text of js/corpus.js): random pieces of different lengths are encrypted with random keys and the key is recovered (300 trials for each length). The optional comparison adds n-gram scoring, which is the same idea with pairs of letters (bigrams) instead of single letters.

Effectiveness and limitations. The success rate grows with the length of the ciphertext, because the letter counts of a short text are noisy and can look like another shift of the language. The attack needs a model of the right language and a text that is typical enough of it, and it works only because the cipher keeps the letter frequencies.

Optional: comparison of the approaches. Exhaustive key search tries all 26 keys, but it needs a way to recognise the right plaintext: a person reading the candidates (see the table above) or a score. Letter-frequency scoring (χ²) does this automatically from the counts of single letters. Bigram scoring uses pairs of letters, which carry more information, and in the test it is right more often on short ciphertexts.

4. Attack on the toy ECC scheme

The weakness used here is the restricted key space. The attacker knows the public key Q and tries d = 1, 2, 3, ..., adding G at each step, until dG = Q. The ciphertext is not needed to find d; once d is known, the message is decrypted like the owner does (js/toyecc.js):

// the attack: try every private key d = from, ..., to until dG = Q (only the public key Q is needed)
function searchKeys(Q, from, to) {
  let P = C.mul(from);
  for (let d = from; d <= to; d++, P = C.add(P, C.G)) {
    if (P.x === Q.x && P.y === Q.y) return d;
  }
  return null;
}

Differences from the attack on the Caesar cipher.

  • The Caesar attack reads the ciphertext: the letter statistics leak the key and a score selects it. The attack on the ECC scheme ignores the ciphertext and uses only the public key.
  • The test on a candidate is statistical for Caesar (χ² can be wrong on short texts) and exact for ECC (dG = Q is true only for the right key), so the ECC attack always succeeds once the whole range is searched.
  • The Caesar attack works because the cipher keeps the statistics of the language, so it would work even with many more keys. The ECC ciphertext shows no statistics: the attack works only because the range of private keys is small.

Why this is not feasible against a properly configured scheme. The search above needs at most 216 = 65,536 steps, and each extra bit of the private key doubles the work. With 256-bit private keys, brute force needs about 2255 ≈ 5.8 · 1076 steps on average. Even the best generic attacks, which need about the square root of the key space (2128 ≈ 3.4 · 1038 steps), would take about 1019 years at 1012 steps per second.

Optional: alternative attacks and where the weaknesses come from.

  • Alternative attacks. Baby-step giant-step (Shanks) and Pollard's rho find d in about √(key space) steps, 28 instead of 216 here. They make the small range even weaker, but they are the reason why 256-bit keys give 128-bit security.
  • From the restricted key space: any search finds d, so the whole scheme is broken. The ephemeral secret r is not restricted, so r alone is of no help.
  • From the design of the toy scheme (present even with a 256-bit private key): no key derivation function (the x-coordinate is used directly as keystream, a hash would be used in practice); no authentication, so the ciphertext can be modified without detection (flipping a bit of c flips the same bit of the message); if r is ever reused, the keystream repeats and c1 XOR c2 = m1 XOR m2; no check that R is a valid point of the curve; and a limit of 32 bytes per block.
