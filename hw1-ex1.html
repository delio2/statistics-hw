Homework 1, exercise 1 - From a private key to a public key on a toy elliptic curve

Scalar multiplication on y² = x³ + 7 (mod 17) and a statistical look at the results.

Elliptic-curve scalar multiplication behaves like a one-way function: from a private key k it is easy to compute the public key Q = kG, but recovering k from Q is believed to be very hard (the elliptic curve discrete logarithm problem, ECDLP). It resembles a hash function in some ways, but it is used for public-key cryptography and digital signatures. Here I compute public keys on a toy curve, explore the statistics of the results, and discuss which properties belong to one-way functions and which to hash functions. The goal is to understand the idea, not to build a real cryptosystem.

1. The toy curve, the base point and the private key

Ethereum uses the curve secp256k1, y² = x³ + 7 over a 256-bit prime. I use the same equation over the field F17, with the base point and the private key suggested by the exercise:

y² = x³ + 7   (mod 17)
G = (1, 5)             base point
k = 6                  private key
Q = kG                 public key

G is on the curve: 5² = 25 ≡ 8 and 1³ + 7 = 8 (mod 17). In the code the curve and G take one line (js/ecc.js):

const toy = new Curve(17n, 7n, { x: 1n, y: 5n });          // y^2 = x^3 + 7 (mod 17), G = (1, 5)

The curve has 17 points plus the point at infinity O, the neutral element (18 in total):


  
G has order n = 9 (nG = O), so only k mod 9 matters. Other points have other orders, shown in the selectors below.


  
2. Point addition

  
Two points are added with the chord-and-tangent rule, with all the arithmetic mod p:

  
P + O = P                    P + (-P) = O,  where -(x, y) = (x, -y)
if P ≠ Q:  λ = (y2 - y1) / (x2 - x1)          (slope of the chord)
if P = Q:  λ = 3x1² / (2y1)                (slope of the tangent, the curve has a = 0)
x3 = λ² - x1 - x2        y3 = λ(x1 - x3) - y1

  
The code (js/ecc.js, methods of the Curve class):

  
// slope of the chord through P and Q, or of the tangent when P = Q (the curve has a = 0)
slope(P, Q) {
  const p = this.p;
  if (P.x === Q.x) return mod(3n * P.x * P.x * inv(2n * P.y, p), p);
  return mod((Q.y - P.y) * inv(Q.x - P.x, p), p);
}

add(P, Q) {
  if (P === null) return Q;
  if (Q === null) return P;
  if (P.x === Q.x && mod(P.y + Q.y, this.p) === 0n) return null;   // Q = -P
  const l = this.slope(P, Q);
  const x = mod(l * l - P.x - Q.x, this.p);
  return { x, y: mod(l * (P.x - x) - P.y, this.p) };
}

  
Division mod p is a multiplication by the modular inverse (inv, extended Euclid algorithm). Worked example, 2G = G + G:
    λ = 3·1² / (2·5) = 3/10. Since 10 · 12 = 120 = 7·17 + 1, the inverse of 10 is 12, so λ = 3·12 = 36 ≡ 2.
    Then x3 = 2² - 2·1 = 2 and y3 = 2(1 - 2) - 5 = -7 ≡ 10, so 2G = (2, 10). It is on the curve: 10² = 100 ≡ 15 = 2³ + 7.

4. A faster method: double-and-add

  
Adding G one at a time needs k - 1 additions, which is hopeless for a 256-bit k. Double-and-add reads the binary digits of k from the most significant one:
    for every digit it doubles the current point, and if the digit is 1 it also adds G. For k = 6 = 1102: start from O; digit 1: double (O) and add G, giving G;
    digit 1: double (2G) and add G, giving 3G; digit 0: double, giving 6G. It needs about log2 k doublings and at most as many additions.

  
// double-and-add, from the most significant bit of k down to the least significant one.
// If steps is an array, every doubling and addition is recorded in it.
mul(k, P = this.G, steps = null) {
  let R = null;
  for (const bit of k.toString(2)) {
    R = this.add(R, R);
    if (steps) steps.push({ op: 'double', bit, R });
    if (bit === '1') {
      R = this.add(R, P);
      if (steps) steps.push({ op: 'add', bit, R });
    }
  }
  return R;
}

    the frequency of each value, the distribution of bits, the apparent uniformity, the correlation between input and output, and avalanche-like behaviour.

  

    
    
    

    

      

      

    

    

    

  

  
The avalanche is measured on the 10-bit encoding of a point (5 bits for x, 5 bits for y): for each k and each bit of k, I flip that bit and count how many output bits change,
    and I compare it with the mean distance between two different outputs chosen at random (js/toystats.js):

  
const enc = (P) => (Number(P.x) << nb) | Number(P.y);
const out = pts.map(enc);
const kbits = (n - 1).toString(2).length;
let sum = 0, cnt = 0;
for (let k = 1; k < n; k++) {
  for (let j = 0; j < kbits; j++) {
    const k2 = k ^ (1 << j);
    if (k2 >= 1 && k2 < n) { sum += popcount(out[k - 1] ^ out[k2 - 1]); cnt++; }
  }
}
// baseline: mean distance between two different outputs chosen at random
let bsum = 0, bcnt = 0;
for (let a = 0; a < m; a++) for (let b = 0; b < m; b++) if (a !== b) { bsum += popcount(out[a] ^ out[b]); bcnt++; }


  
7. Discussion: one-way function or hash function?

  
A one-way function and a cryptographic hash function share the idea of being easy to compute and hard to invert, but they do different jobs,
    so not every statistical property is meaningful for both.

  

    
PropertyOne-way function kG (public-key use)Cryptographic hash function

    
      
One-waynessEssential. It rests on the ECDLP, a mathematical problem.Essential (preimage resistance). It rests on the design and on cryptanalysis.

      
Distribution of the output, bit balance, uniformityDesirable: a public key should not leak structure about k. On the toy curve the outputs are a permutation of a subgroup, so they are exactly uniform on it by construction, which says nothing about security.Required: every output bit should be unbiased and the output should look random for any input.

      
Frequency of values, collisionsNot a goal. kG is injective for k = 1, ..., n - 1, so there are no collisions, but there is no compression either: the input is a scalar mod n, the output a point of about the same size.Required: collision resistance, with an input of any length compressed to a fixed length.

      
Correlation between input and outputNo useful correlation, but there is exact algebraic structure: (a + b)G = aG + bG, which is what makes key agreement and signatures possible, and x(kG) = x((n - k)G).No correlation at all. Algebraic structure such as linearity is a weakness.

      
Avalanche effectNot required: the security comes from the ECDLP, not from diffusion.A design goal: flipping one input bit should flip each output bit with probability 1/2 (strict avalanche criterion).

    
  

  
What the exploration showed:

  
    
    
  • Structure. Every point appears once and every x value twice: kG and (n - k)G are opposite points with the same x (the only exception is the point with y = 0, which is its own opposite),
      so x alone loses one bit. The linear correlation between k and x is exactly 0 even though x depends on k: the coefficient only detects linear dependence.
    • 
    
  • Bits. The numbers 0 to 16 need 5 bits, but the top bit is 1 only for the value 16, so it is almost always 0. This comes from the tiny modulus and would disappear with a 256-bit prime.
    • 
    
  • Small sample. With at most 17 points the chi-square test is not reliable and the avalanche comparison is rough: the toy curve shows structure, not strong statistics.
    • 
  

  
Statistical tests are necessary but not sufficient: they can reveal defects, they cannot prove one-wayness. The toy key may look random, yet it is broken by trying every k (at most n - 1 additions),
    while secp256k1 has about 2256 points and the best generic attacks need about 2128 operations. Uniformity, avalanche and the absence of structure are the properties asked specifically
    of hash functions; for kG the guarantee is the hardness of the ECDLP.
