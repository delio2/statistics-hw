Homework 2 - From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline, and their statistical properties.

A wallet does not store a list of addresses. It keeps one secret and derives everything else from it. In this homework I follow the whole path from the mnemonic phrase to a checksummed Ethereum address, explain the role of each standard and primitive, put them in their historical context, and look at their statistical properties. Instead of using a wallet application, I implemented the pipeline in JavaScript and checked it against public test vectors.

3. The six building blocks

BIP-39: mnemonic sentence and seed

Purpose: a backup of the secret that a human can write down. A random entropy of 128 to 256 bits (a multiple of 32) receives a checksum, the first ENT/32 bits of its SHA-256 hash, and the result is cut in groups of 11 bits. Each group is the index of a word in a fixed list of 2048 words, so 128 bits give 12 words and 256 bits give 24. The checksum lets a wallet notice a mistyped phrase.

With the all-zero entropy the indices are eleven 0 and one 3, which in the official English list are the words "abandon" (index 0) and "about" (index 3): this is the test phrase used above. The mnemonic is then turned into a seed. The seed does not need the word list, because it is computed from the text of the phrase (js/wallet.js):

// seed = PBKDF2-HMAC-SHA512(password = mnemonic, salt = "mnemonic" + passphrase, 2048 iterations, 64 bytes)
async function mnemonicToSeed(mnemonic, passphrase = '') {
  const key = await subtle.importKey('raw', utf8(mnemonic.normalize('NFKD')), 'PBKDF2', false, ['deriveBits']);
  const salt = utf8('mnemonic' + passphrase.normalize('NFKD'));
  return new Uint8Array(await subtle.deriveBits({ name: 'PBKDF2', hash: 'SHA-512', salt, iterations: 2048 }, key, 512));
}

The salt is the string "mnemonic" followed by an optional passphrase, so the same phrase with another passphrase gives a completely different wallet. The 2048 iterations make every guess more expensive for an attacker.

BIP-32: hierarchical deterministic (HD) key derivation

Purpose: one seed, a whole tree of keys. The master private key and a chain code are the two halves of HMAC-SHA512 with key "Bitcoin seed" applied to the seed. A child key is computed from the parent key, the parent chain code and an index: I = HMAC-SHA512(chain code, data), the child key is the left half of I plus the parent key (mod n), and the right half of I is the new chain code. Indexes from 231 on are hardened (the data contains the parent private key); the others use the parent public key. Nothing has to be stored except the seed, and the same seed always rebuilds the same tree (js/wallet.js):

// child key derivation (private parent -> private child)
async function childKey(parent, index) {
  const k = bytesToBig(parent.key);
  const data = index >= HARDENED
    ? concat(Uint8Array.of(0), parent.key, ser32(index))                        // hardened: uses the private key
    : concat(E.hexToBytes(E.compress(C.mul(k))), ser32(index));                  // normal: uses the public key
  const I = await hmacSha512(parent.chain, data);
  const il = bytesToBig(I.slice(0, 32));
  const child = (il + k) % C.n;
  if (il >= C.n || child === 0n) throw new Error('invalid key (probability < 2^-127): use the next index');
  return { key: bigToBytes(child), chain: I.slice(32) };
}

BIP-44: standard derivation paths

Purpose: a convention so that different wallets find the same accounts. The path is m / purpose' / coin_type' / account' / change / address_index, where the apostrophe means hardened. The purpose is 44, the coin type is 60 for Ethereum (the numbers are listed in the SLIP-44 registry), then the account number, 0 for external addresses, and the index of the address. So m/44'/60'/0'/0/0 is the first address of the first Ethereum account, the one many wallets, such as MetaMask, show first.

secp256k1: public-key cryptography

Purpose: to turn a private key into a public key that anyone can use to check signatures. The private key is a 256-bit integer k between 1 and n - 1, and the public key is the point Q = kG of the curve y² = x³ + 7, the same arithmetic as in Homework 1 but over a 256-bit prime field. Going back from Q to k is the elliptic curve discrete logarithm problem, which costs about 2128 operations. The curve is defined in SEC 2 and Bitcoin has used it since 2009; Ethereum signs transactions with ECDSA on it. Ethereum uses the 64 bytes x and y of the public key (js/wallet.js):

function publicKey(privateKey) {                 // the 64 bytes x || y (Ethereum drops the 0x04 prefix)
  const Q = C.mul(bytesToBig(privateKey));
  return { x: Q.x, y: Q.y, bytes: concat(bigToBytes(Q.x), bigToBytes(Q.y)) };
}

const addressBytes = (pubBytes) => K.keccak256(pubBytes).slice(12);          // last 20 bytes of Keccak-256

Keccak-256: hashing

Purpose: to compress the 64-byte public key into a short, fixed-size identifier. Ethereum computes Keccak-256 of x and y and keeps the last 20 bytes (160 bits): that is the address (the last line of the code above). Keccak is a sponge: the message is absorbed, block by block, into a 1600-bit state through the permutation Keccak-f (24 rounds); with a rate of 1088 bits and a capacity of 512 bits, 256 bits are then squeezed out. It is a hash function: no key, a fixed-size output, and it is easy to compute but hard to invert.

EIP-55: mixed-case checksum

Purpose: to detect typing errors in an address without changing its format. Take the lower-case hexadecimal address (without 0x), compute the Keccak-256 hash of that text, and write each letter a to f in capitals if the corresponding hexadecimal digit of the hash is 8 or more. The pattern of capitals is the checksum; software that ignores the case still reads the address (js/wallet.js):

// EIP-55: a hex letter is written in upper case when the matching nibble of Keccak-256(lower-case address) is >= 8
function toChecksumAddress(addressHex) {
  const lower = addressHex.toLowerCase().replace(/^0x/, '');
  const hash = toHex(K.keccak256(utf8(lower)));
  let out = '0x';
  for (let i = 0; i < lower.length; i++) {
    out += /[a-f]/.test(lower[i]) && parseInt(hash[i], 16) >= 8 ? lower[i].toUpperCase() : lower[i];
  }
  return out;
}

4. Key generation, derivation, public-key cryptography, hashing, checksums and encoding

These five ideas are easy to confuse. In the pipeline they are clearly separated:

ConceptWhat it isIn the pipeline
Key generationCreating new secret randomness. It needs a good random source.Choosing the random entropy of the mnemonic. It is the only random step.
Key derivationComputing keys deterministically from a secret that already exists: the same input always gives the same keys.PBKDF2 (mnemonic to seed), HMAC-SHA512 in BIP-32 (the key tree), the BIP-44 path (which key of the tree).
Public-key cryptographyA pair of keys linked by a one-way operation: the public key can be shared, and only the private key can sign.secp256k1: Q = kG.
HashingA keyless function that maps any input to a fixed-size digest and cannot be inverted.Keccak-256 (address), SHA-256 (BIP-39 checksum), SHA-512 inside PBKDF2 and HMAC.
ChecksumRedundancy that detects accidental errors. It gives no secrecy and no protection against an attacker.The checksum bits of the mnemonic and the capital letters of EIP-55.
EncodingA reversible way to write data. It has nothing to do with security.Words (11 bits per word), hexadecimal, the 0x prefix, upper and lower case.

A hash is not encryption, an encoding is not secret, and a checksum is not a signature.

The order is: public-key cryptography first, then the hash standards, then the wallet conventions that join them. The wallet standards (2012 to 2014) came from Bitcoin and were reused by Ethereum.

They are related historically and both are cryptographic hash functions. SHA-3 was chosen with a completely different design from SHA-2, so that a weakness found in one family would not affect the other. Ethereum was built on the Keccak submission before the standard was final. Then NIST added domain-separation bits to the padding in FIPS 202 (the suffix 0x06 for SHA3-256 instead of 0x01), so Ethereum's Keccak-256 is not the standardised SHA3-256: the permutation is the same, the padding is different, and the digests are different. 6. Why several different primitives?

Each step has its own job and its own security goal, so no single algorithm could do everything:

  • BIP-39 / BIP-32 / BIP-44: key management and derivation. They make one short secret enough to rebuild every key, they give a standard way to back it up (words) and to organise accounts (paths), so that different wallets agree.
  • secp256k1: the relation between private and public key, and signatures. Only this step lets someone prove ownership without revealing the secret and lets everyone check it. A hash function has no such key pair.
  • Keccak-256: hashing. It shortens the public key to a fixed 20-byte identifier. A curve cannot compress arbitrary data in that way.
  • EIP-55: checksum and error detection. It protects against typing mistakes, which none of the other steps does, and it does so without changing the address format.

Going down the pipeline is easy and going up is hard, so the public values (public key and address) can be shown to anyone, while the seed and the private key must be kept secret. Separating the steps also lets each one be reused or replaced on its own: for example, BIP-39 and BIP-32 are shared by Bitcoin and Ethereum wallets.

7. Statistical properties

Each step needs its output to look uniformly random and unrelated to its input; otherwise a secret could be guessed or two identifiers could collide.

  • Entropy of the phrase. A 12-word phrase carries 128 bits (132 encoded bits minus 4 checksum bits), a 24-word phrase 256 bits. Searching 2128 possibilities is out of reach, but only if the entropy comes from a good random source: a phrase chosen by hand has far fewer bits.
  • Seed. The PBKDF2-HMAC-SHA512 output should be indistinguishable from 512 random bits. The 2048 iterations multiply by 2048 (about 11 bits) the work needed to test one guess of the passphrase, but they add no entropy.
  • BIP-32. Each HMAC-SHA512 gives 512 pseudo-random bits. A child key would be invalid only if the left half were n or more, or the key were 0, which has probability below 2-127: it never happens in practice.
  • Public key. The x-coordinate of kG looks uniform, as the secp256k1 tests of Homework 1 show.
  • Address. Only 160 bits are kept. Finding two keys with the same address costs about 280 operations (birthday bound); finding a key for a given address costs about 2160, more than the 2128 needed to break the curve itself.
  • EIP-55. A 40-digit random address contains on average 40 · 6/16 = 15 letters, and each letter carries one check bit. A random typo passes the check with probability (13/16)40 = 0.0247% on average, about 1 in 4000, while an all-lower-case address has no check at all. An address with no letters has no checksum either.

The hash functions can also be tested statistically. I feed the three functions of this homework with random 64-byte inputs (the size of a public key) and run the same tests as in Homework 1: avalanche (flipping one input bit should flip each output bit with probability 1/2), bit balance, uniformity of the bytes (chi-square) and collisions on 16 truncated bits.

The three functions pass in the same way. Keccak-256 and SHA3-256 are statistically indistinguishable, as expected for two functions that differ only in one padding byte, and SHA-256, from the other family, behaves in the same way too. This is what the tests can say: that the common requirement holds. They cannot tell the families apart, and they cannot prove collision or preimage resistance.
