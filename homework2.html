1. Overview

A blockchain is a ledger copied on many computers that do not trust each other. Cryptography gives the building blocks (hashes, signatures). Statistics and probability describe how the system behaves and how it can be attacked, because mining, randomness and attacker power are random quantities.

2. Mining as a Poisson process

To mine a Bitcoin block a miner varies a nonce until SHA-256(SHA-256(header)), read as a number, is below a target T. If the hash behaves like a uniform random value, each attempt succeeds with the tiny probability p = T / 2256, independently of all the others. A long sequence of independent, rare Bernoulli trials gives:

  • the number of blocks found in a time window is approximately Poisson, with rate λ = (hash rate) · p;
  • the time between blocks is exponential with mean 1/λ, and it is memoryless: having waited 20 minutes does not make the next block closer.

The protocol aims at 10 minutes per block on average and adjusts the difficulty every 2016 blocks (about two weeks). A block needs on average D · 232 hashes, where D is the difficulty, so the network hash rate is about D · 232 / 600 hashes per second. This is an estimate from a finite sample: the sum of 2016 exponential times has relative standard deviation 1/√2016 ≈ 2.2%, which is the statistical error of each difficulty adjustment.

3. How many confirmations? The attacker catch-up probability

An attacker with a fraction q of the hash power secretly mines a competing chain, while honest miners (fraction p = 1 - q) extend the real one. After a merchant waits for z confirmations, what is the chance the attacker ever catches up? Nakamoto's white paper (section 11) models the attacker's progress as a Poisson variable with mean λ = z·q/p, and then uses the gambler's-ruin result (catch-up from a deficit of k blocks with probability (q/p)k if q < p):

P(attacker catches up) = 1 - Σk=0..z [ λk e-λ / k! ] · ( 1 - (q/p)z-k )

Implementation (js/hw2.js). The Poisson term is built iteratively, starting from e-λ and multiplying by λ/k at each step, so no factorial is needed:

function catchUp(q, z) {
  const p = 1 - q;
  if (q >= p) return 1;
  const lam = (z * q) / p;
  let pois = Math.exp(-lam), sum = 0;
  for (let k = 0; k <= z; k++) {
    if (k > 0) pois *= lam / k;
    sum += pois * (1 - Math.pow(q / p, z - k));
  }
  return 1 - sum;
}

The probability falls exponentially with z when q < 1/2, which is why 6 confirmations (about an hour) became the common convention for large payments; the table reproduces the values published by Nakamoto for q = 0.1 and q = 0.3. If q ≥ 1/2 the attacker always wins eventually. Statistics also shows that "majority is not enough": Eyal and Sirer (2014) proved that a miner who withholds blocks strategically (selfish mining) can earn more than a fair share with less than half of the hash power. The threshold is 1/3 if the attacker never wins a tie, 1/4 if it wins half of the ties, and any positive share if it always wins them.

4. When randomness fails: ECDSA nonce reuse

An ECDSA signature of a message hash z with private key d uses a fresh random nonce k:

r = x(k·G) mod n        s = k-1 (z + r·d) mod n

Security needs k to be uniform on [1, n-1] and used once. If the same k signs two different messages, r is the same, and then k = (z1 - z2) / (s1 - s2) and d = (s1·k - z1) / r: two public signatures give away the private key. This really happened: Sony's PS3 signing key was recovered in 2010 because the console used a constant nonce, and in 2013 a flaw in Android's random generator produced repeated r values in Bitcoin transactions and allowed theft of funds. Even a biased nonce is dangerous: knowing only a few bits of each nonce over many signatures lets an attacker solve a lattice problem and recover the key (Howgrave-Graham and Smart, 2001; Breitner and Heninger, 2019, applied it to real Bitcoin and Ethereum signatures). So the quality of the random numbers is a security problem, not just a detail of statistics.

The demonstration below signs two messages with the same nonce and then recovers the key using only public values (js/hw2.js):

const r = mul(k).x % N;
const kinv = inv(k, N);
const s1 = mod(kinv * (z1 + r * d), N);
const s2 = mod(kinv * (z2 + r * d), N);

// attacker's side: only (z1, z2, r, s1, s2) are used
const kRec = mod((z1 - z2) * inv(s1 - s2, N), N);
const dRec = mod((s1 * kRec - z1) * inv(r, N), N);

5. Statistics as an analysis tool

  • De-anonymisation. Addresses are pseudonyms. Heuristics such as "all inputs of one transaction belong to the same owner" let analysts cluster addresses and link them to exchanges or services (Meiklejohn et al., 2013). Privacy tools try to defeat these inferences, and the arms race is statistical.
  • Anomaly and fraud detection. Benford's law says the leading digit d of many natural datasets appears with probability log10(1 + 1/d) (30.1% for 1, 4.6% for 9). Amounts that deviate strongly can flag wash trading or fabricated data, though a deviation alone is never proof.
  • Proof of stake. In Ethereum the block proposer of each 12-second slot is chosen pseudo-randomly (the probability depends on the stake of the validator) and the validators are shuffled into committees, using a shared source of randomness (RANDAO). Whether this randomness is fair and hard to manipulate is again a statistical question.

6. Conclusion

In this homework I looked at how cryptography and statistics work together in Bitcoin and Ethereum. Mining is a Poisson process, so block times are random and a confirmation is only a probabilistic guarantee. Signatures are as strong as the randomness of their nonces, and many real attacks hit the random numbers, not the mathematics of the algorithms. The toy hash of Homework 1 follows the same idea on a small scale: the algebra gives the structure and the statistical tests check that the output behaves as the security argument assumes.
