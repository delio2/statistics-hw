Homework 1, exercise 2 - From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline, and their statistical properties.

A wallet does not store a list of addresses: it keeps one secret and derives everything else from it. In this homework I follow the path from the mnemonic phrase to a checksummed Ethereum address, say what each standard and primitive does, put them in their historical context and look at their statistical properties.

3. The six building blocks

BIP-39: mnemonic sentence and seed

Purpose: a backup of the secret that a human can write down. A random entropy of 128 to 256 bits (a multiple of 32) gets a checksum, the first ENT/32 bits of its SHA-256 hash, and the result is cut in groups of 11 bits. Each group is the index of a word in a fixed list of 2048 words, so 128 bits give 12 words and 256 bits give 24. In the example, 128 zero bits have checksum bits 0011, so the groups are eleven times 00000000000 (word 0, "abandon") and 00000000011 (word 3, "about"). The phrase is then turned into the seed with PBKDF2-HMAC-SHA512 (2048 iterations, salt "mnemonic" plus an optional passphrase): the same phrase and passphrase always give the same seed, and another passphrase gives a completely different wallet.

BIP-32: hierarchical deterministic (HD) key derivation

Purpose: one seed, a whole tree of keys. The master private key and a chain code are the two halves of HMAC-SHA512 with key "Bitcoin seed" applied to the seed. A child key is computed from the parent key, the parent chain code and an index: I = HMAC-SHA512(chain code, data); the child key is the left half of I plus the parent key (mod n), and the right half of I is the new chain code. Indexes from 231 on are hardened (the data contains the parent private key); the others use the parent public key. Only the seed has to be stored, and the same seed always rebuilds the same tree.

BIP-44: standard derivation paths

Purpose: a convention so that different wallets find the same accounts. The path is m / purpose' / coin_type' / account' / change / address_index, where the apostrophe means hardened. The purpose is 44, the coin type is 60 for Ethereum (the numbers are in the SLIP-44 registry), then the account, 0 for external addresses, and the index of the address. So m/44'/60'/0'/0/0 is the first address of the first account, the one many wallets, such as MetaMask, show first.

secp256k1: public-key cryptography

Purpose: to turn the private key into a public key that anyone can use to check signatures. The private key is an integer k between 1 and n - 1 (256 bits), and the public key is the point Q = kG of the curve y² = x³ + 7, the arithmetic of exercise 1 over a 256-bit prime; Ethereum uses its 64 bytes x and y. Going back from Q to k is the elliptic curve discrete logarithm problem, which costs about 2128 operations. The curve is defined in SEC 2 and Bitcoin has used it since 2009; Ethereum signs transactions with ECDSA on it.

Keccak-256: hashing

Purpose: to compress the 64-byte public key into a short, fixed-size identifier: the address is the last 20 bytes (160 bits) of the Keccak-256 hash of x and y. Keccak is a sponge: the message is absorbed, block by block, into a 1600-bit state through the permutation Keccak-f (24 rounds), and then 256 bits are squeezed out. It is a hash function: no key, a fixed-size output, easy to compute and hard to invert.

EIP-55: mixed-case checksum

Purpose: to detect typing errors in an address without changing its format. Take the lower-case hexadecimal address (without 0x), compute the Keccak-256 hash of that text, and write each letter a to f in capitals if the corresponding hexadecimal digit of the hash is 8 or more. The capitals are the checksum, and software that ignores the case still reads the address. In the example, 9858effd... becomes 9858EfFD....

4. Key generation, derivation, public-key cryptography, hashing, checksums and encoding

ConceptWhat it isIn the pipeline
Key generationCreating new secret randomness. It needs a good random source.Choosing the random entropy of the mnemonic. It is the only random step.
Key derivationComputing keys deterministically from a secret that already exists: the same input always gives the same keys.PBKDF2 (mnemonic to seed), HMAC-SHA512 in BIP-32 (the key tree), the BIP-44 path (which key of the tree).
Public-key cryptographyA pair of keys linked by a one-way operation: the public key can be shared, and only the private key can sign.secp256k1: Q = kG.
HashingA keyless function that maps any input to a fixed-size digest and cannot be inverted.Keccak-256 (address), SHA-256 (BIP-39 checksum), SHA-512 inside PBKDF2 and HMAC.
ChecksumRedundancy that detects accidental errors. It gives no secrecy and no protection against an attacker.The checksum bits of the mnemonic and the capital letters of EIP-55.
EncodingA reversible way to write data. It has nothing to do with security.Words (11 bits per word), hexadecimal, the 0x prefix, upper and lower case.

A hash is not encryption, an encoding is not secret, and a checksum is not a signature.

5. Historical context

YearTechnologyNote

2001SHA-2 (SHA-256, SHA-512, ...)NIST standard (FIPS 180-2, final in 2002). SHA-256 gives the BIP-39 checksum, SHA-512 is inside PBKDF2 and HMAC.
2012BIP-32Hierarchical deterministic wallets.
2013BIP-39Mnemonic code for deterministic wallets.
2014BIP-44Multi-account hierarchy: standard paths.

2016EIP-55Mixed-case checksum for Ethereum addresses.

The order is: public-key cryptography first, then the hash standards, then the wallet conventions that join them. The wallet standards (2012 to 2014) came from Bitcoin and were reused by Ethereum.

They are related historically and both are cryptographic hash functions. SHA-3 was chosen with a completely different design from SHA-2, so that a weakness found in one family would not affect the other. Ethereum was built on the Keccak submission before the standard was final. Then NIST added domain-separation bits to the padding in FIPS 202 (the suffix 0x06 for SHA3-256 instead of 0x01), so Ethereum's Keccak-256 is not the standardised SHA3-256: the permutation is the same, the padding is different, and the digests are different. 6. Why several different primitives?

Each step has its own job and its own security goal, so no single algorithm could do everything:

  • BIP-39 / BIP-32 / BIP-44: key management and derivation. One short secret is enough to rebuild every key; there is a standard way to back it up (words) and to organise accounts (paths), so that different wallets agree.
  • secp256k1: the relation between private and public key, and digital signatures. Only this step lets someone prove ownership without revealing the secret and lets everyone check it. A hash function has no such key pair.
  • Keccak-256: hashing. It shortens the public key to a fixed 20-byte identifier. A curve cannot compress arbitrary data in that way.
  • EIP-55: checksum and error detection. It protects against typing mistakes, which none of the other steps does, and it does so without changing the address format.

Going down the pipeline is easy and going up is hard, so the public values (public key and address) can be shown to anyone, while the seed and the private key must be kept secret.

7. Statistical properties

Each step needs its output to look uniformly random and unrelated to its input; otherwise a secret could be guessed or two identifiers could collide.

StepStatistical requirementNumbers
Entropy (BIP-39)Uniformly random bits from a good random source.12 words = 128 bits (132 encoded bits minus 4 checksum bits), 24 words = 256 bits. A phrase chosen by hand has far fewer bits.
Seed (PBKDF2-HMAC-SHA512)Output indistinguishable from 512 random bits.The 2048 iterations multiply by 2048 (about 11 bits) the work to test one guess of the passphrase; they add no entropy.
Child keys (BIP-32)Each key pseudo-random and unrelated to its parent.A child key is invalid only if the left half of I is n or more, or the key is 0: probability below 2-127.
Public key (secp256k1)x(kG) should look uniform and reveal nothing about k.At 256 bits the points are expected to look random (the toy curve of exercise 1 is too small to show it). Finding k costs about 2128 operations.
Address (Keccak-256, 160 bits)Uniform output and avalanche: flipping one input bit flips each output bit with probability 1/2.Finding two keys with the same address costs about 280 operations (birthday bound); finding a key for a given address about 2160, more than the 2128 of the curve.
Checksum (EIP-55)Check bits that behave like random bits.A random address has on average 40 · 6/16 = 15 letters, each one a check bit. A random typo passes a digit with probability 10/16 + (6/16)(1/2) = 13/16, so the whole address with probability (13/16)40 = 0.0247%, about 1 in 4000. An all-lower-case address has no check at all.

Statistical checks of a hash function (bit balance, avalanche, uniformity, collisions) can reveal defects, as in exercise 1, but they cannot prove collision or preimage resistance.
